# Diccionario de Datos — GuateCompras

**Sistema de Gestión de Adquisiciones y Proveedores** · Bases de Datos I · Universidad Mariano Gálvez de Guatemala (Salamá, Baja Verapaz)


## Convenciones

- **Llave:** PK = clave primaria, FK = clave foránea, UK = restricción UNIQUE.
- **Nulo:** «Sí» si la columna acepta NULL.
- **Tipo:** se muestra el tipo de SQL Server. Donde PostgreSQL usa otro tipo, aparece como `SQL Server / PostgreSQL`. `INT (IDENTITY)` es `INT GENERATED BY DEFAULT AS IDENTITY` en PostgreSQL.
- Las filas marcadas con **(nuevo)** son campos agregados respecto a la versión anterior del diccionario. Las tablas marcadas con **(tabla nueva)** no existían en esa versión.

## Cambios respecto a la versión anterior

- **Tablas nuevas:** `SucursalTelefono`, `ProveedorRubro` y `Auditoria`.
- **Columna `estado`** (Activo / Inactivo) en `Articulo` y `Proveedor`.
- **Columna `observaciones`** (VARCHAR(300), nullable) en `OrdenCompra`, `Oferta` y `Adjudicacion`.
- **`RelacionComercial`:** nuevo CHECK que obliga a `id_proveedor_a < id_proveedor_b`, de modo que cada par se guarda en un solo orden.
- **`SubtipoOrden`:** nuevas restricciones `UNIQUE (id_tipo, nombre)` y `UNIQUE (id_tipo, id_subtipo)`.
- **`OrdenCompra`:** nueva FK compuesta `(id_tipo, id_subtipo) → SubtipoOrden`, que garantiza que el subtipo pertenezca al tipo.
- **Vista, índices y 8 triggers de integridad nuevos** (secciones finales).
- Se mantienen sin cambios los triggers de fechas de la versión anterior.

### RelacionComercial

*Registra si dos proveedores tienen relación comercial entre sí (ej. mismo conglomerado).*

| Campo | Tipo de dato | Nulo | Llave | Descripción y restricciones |
|---|---|---|---|---|
| `id_relacion_comercial` | INT (IDENTITY) | No | PK | Identificador interno. |
| `id_proveedor_a` | INT | No | FK | → Proveedor.id_proveedor. Siempre el id menor del par. |
| `id_proveedor_b` | INT | No | FK | → Proveedor.id_proveedor. Siempre el id mayor del par. |

**Reglas y restricciones de tabla:**

- UQ_RelacionComercial_Par: UNIQUE (id_proveedor_a, id_proveedor_b), sin pares duplicados.

### OrdenCompra

*Agrupa uno o varios pedidos para iniciar el proceso de cotización.*

| Campo | Tipo de dato | Nulo | Llave | Descripción y restricciones |
|---|---|---|---|---|
| `id_orden` | INT (IDENTITY) | No | PK | Identificador interno. |
| `descripcion` | VARCHAR(200) | No | — | Descripción de la orden. |
| `fecha_creacion` | DATE | No | — | No puede ser anterior a la fecha_solicitud de ninguno de sus pedidos (trigger). |
| `fecha_limite_oferta` | DATE | No | — | Fecha límite para recibir ofertas. CHECK (fecha_limite_oferta >= fecha_creacion). |
| `id_tipo` | INT | No | FK | → TipoOrden.id_tipo. |
| `id_subtipo` | INT | Sí | FK | → SubtipoOrden.id_subtipo. NULL si la orden no tiene subtipo (ej. «Grande»). |
| `observaciones` | VARCHAR(300) | Sí | — | Observaciones libres. **(nuevo)** |

**Reglas y restricciones de tabla:**

- FK compuesta FK_OrdenCompra_TipoSubtipo: (id_tipo, id_subtipo) → SubtipoOrden(id_tipo, id_subtipo). Garantiza que el subtipo pertenezca al tipo de la orden. Con id_subtipo NULL la FK no se evalúa.
- El DDL no obliga a que una orden «Chica» tenga subtipo ni a que una «Grande» no lo tenga: eso depende de los datos cargados en SubtipoOrden y de la validación de la aplicación.
- Triggers: tr_OrdenCompra_Integridad (fechas y subtipo) y tr_OrdenCompra_Ofertas (no dejar ofertas fuera del nuevo plazo).

## Triggers

Los CHECK de SQL no pueden consultar otras tablas, por lo que las reglas que comparan datos entre tablas se implementan como triggers. En SQL Server los errores usan `THROW` con los códigos indicados; en PostgreSQL se usa `RAISE EXCEPTION` con el mismo mensaje.

| Trigger | Tabla · Evento | Qué valida | Código de error (SQL Server) |
|---|---|---|---|
| `TRG_Pedido_ValidaFechaOrden / trg_pedido_valida_fecha_orden` | Pedido · INSERT, UPDATE | La fecha_creacion de la orden asignada no puede ser anterior a la fecha_solicitud del pedido. | RAISERROR |
| `TRG_Adjudicacion_ValidaFecha / trg_adjudicacion_valida_fecha` | Adjudicacion · INSERT, UPDATE | La fecha_resolucion no puede ser anterior a la fecha_creacion de la orden. | RAISERROR |
| `tr_Oferta_Integridad` | Oferta · INSERT, UPDATE | El pedido debe estar asignado a una orden, la fecha_oferta debe caer dentro del plazo de la orden y el proveedor debe tener el artículo en su catálogo. | 51001, 51002 |
| `tr_DetalleAdjudicacion_Integridad` | DetalleAdjudicacion · INSERT, UPDATE | Pedido y oferta deben corresponder a la misma orden de la adjudicación; la oferta debe ser de ese pedido, no posterior a la fecha de resolución, y cantidad_final no puede superar la cantidad pedida. | 51003 |
| `tr_OrdenCompra_Integridad` | OrdenCompra · INSERT, UPDATE | fecha_creacion no puede ser anterior a la solicitud de sus pedidos ni posterior a su adjudicación; el subtipo debe pertenecer al tipo. | 51004, 51005, 51006 |
| `tr_Pedido_Historial` | Pedido · UPDATE | Un pedido con ofertas no puede cambiar de orden ni de artículo; la cantidad no puede quedar menor que la adjudicada. | 51007, 51008 |
| `tr_Adjudicacion_Historial` | Adjudicacion · UPDATE | La resolución no puede contradecir los pedidos u ofertas ya adjudicados (misma orden; oferta no posterior a la fecha). | 51009 |
| `tr_Oferta_Historial` | Oferta · UPDATE | Una oferta adjudicada no puede modificar proveedor, pedido, precio ni fecha. | 51010 |
| `tr_OrdenCompra_Ofertas` | OrdenCompra · UPDATE | Las nuevas fechas no pueden dejar ofertas existentes fuera del plazo. | 51011 |
| `tr_ProveedorArticulo_Historial` | ProveedorArticulo · DELETE | No se puede eliminar una relación de catálogo si el proveedor tiene ofertas históricas de ese artículo. | 51012 |

## Reglas de negocio del enunciado y dónde se implementan

| Regla | Implementación |
|---|---|
| La fecha de creación de la orden no puede ser anterior a la fecha de solicitud de ninguno de sus pedidos. | TRG_Pedido_ValidaFechaOrden y tr_OrdenCompra_Integridad |
| La fecha de adjudicación no puede ser anterior a la fecha de creación de la orden. | TRG_Adjudicacion_ValidaFecha |
| El nombre del departamento puede repetirse entre sucursales, no dentro de la misma. | UQ_Departamento_SucursalNombre (UNIQUE id_sucursal, nombre) |
| Las órdenes son «Grandes» o «Chicas»; las «Chicas» pueden ser «Urgentes» o «Normales». | TipoOrden, SubtipoOrden, sus CHECK y la FK compuesta de OrdenCompra |
| Un proveedor oferta solo artículos de su catálogo, dentro del plazo de la orden. | tr_Oferta_Integridad |
| Una adjudicación se registra una sola vez por orden, con un detalle por pedido. | UNIQUE en Adjudicacion.id_orden y UQ_DetalleAdjudicacion_AdjPedido |

## Diferencias entre el script de SQL Server y el de PostgreSQL

| Aspecto | SQL Server | PostgreSQL |
|---|---|---|
| Autoincremento | INT IDENTITY(1,1) | INT GENERATED BY DEFAULT AS IDENTITY |
| Booleanos | BIT (0 / 1) | BOOLEAN (FALSE / TRUE) |
| Entero pequeño | TINYINT | SMALLINT |
| Fecha y hora | DATETIME2, SYSUTCDATETIME() (UTC) | TIMESTAMP, CURRENT_TIMESTAMP (zona horaria de la sesión) |
